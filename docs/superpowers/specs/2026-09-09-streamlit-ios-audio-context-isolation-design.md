# Streamlit iOS 录音上下文隔离与断续拦截设计

日期：2026-09-09  
状态：家长已批准方案 A

## 问题证据

- `S4A-T1-W01-D02` 第 3 题第二次录音的 WAV 长 6.997 秒。
- 文件内出现 41 段全零静音；主要静音段均约 85.3ms，并以约 170.7ms 周期交替出现。
- 85.3ms 正好对应 48kHz 下 `ScriptProcessor(4096)` 的一个输入缓冲块，证明断续已经写进原始 WAV，不是网络回放或讯飞评分造成。
- 线上仍包含 2026-09-07 的“每次重新获取麦克风流”修复；今天暴露的是复用同一个 `AudioContext` 后的第二层故障。

## 实施范围

1. 每次用户点击录音时，在用户手势调用栈中创建新的 `AudioContext`。
2. 每次录音完成、失败、放弃或题目切换时，断开节点、停止麦克风流并关闭当次 `AudioContext`；不跨录次复用。
3. 在编码和评分前检查原始 4096 采样缓冲块。若存在大量“全零块/有声块”严格交替，判定本次采集断续。
4. 断续录音直接作废，恢复可点击的话筒，提示重新录制；不上传、不调用讯飞、不消耗录次。
5. 保持 16kHz 单声道 PCM WAV、倒计时、最长录音、静音阈值、评分门控、课程内容和历史数据不变。

## 验证

- 静态回归测试确认每录次新建/关闭上下文，且断续检查发生在 WAV 编码之前。
- 浏览器运行时模拟连续正常缓冲与交替全零缓冲：正常录音进入回听，异常录音回到可重录状态且不向 Streamlit 发送录音值。
- 执行项目完整自动化测试，并在上线后核对生产组件实际代码。
- 自动化不能代替 iPad 麦克风硬件；生产上线后只需一次短句真机回听和评分复核。
